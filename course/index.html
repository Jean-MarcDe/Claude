Tokens to Pull Requests

Part One explains how a modern language model actually works, from gradient descent to agents. Part Two spends that understanding inside GitHub Enterprise — on instruction files, prompts, code review, coding agents and the governance around them.

Two parts · 14 modules · 20 figures · 8 labs
Reading time ≈ 4 hours · Full workshop ≈ 2 days
Audience: engineers, tech leads and platform owners. No maths beyond school algebra.

Why the theory comes first

Most teams learn AI tooling as a list of tricks: add this file, say “think step by step”, pick that model. The tricks work until they don't, and then nobody can say why — because the tricks were never connected to a mechanism.

Almost every practical rule in Part Two is a direct consequence of something mechanical in Part One. Instruction files have to be short because they compete with your code for a fixed token budget. A coding agent needs a green test suite because the loop has no other error signal. You cannot sanitise your way out of prompt injection because the model reads instructions and data through the same channel. None of that is memorisable as a tip. All of it is obvious once you can see the machine.

So Part One builds the machine, and every concept block ends with a bridge marker pointing at the practice it determines. Part Two points back.

The bridge

This table is the spine of the course. Read it now as a promise, and again at the end as a summary.

Mechanism (Part One)Consequence you can act on (Part Two)
The context window is a fixed token budgetInstruction files compete with your source code. Short and specific beats thorough.
Tokenisation is tuned for English and for codeThe same instruction costs 1.5–2× more tokens in German or Japanese. Write durable repo instructions in English.
Attention degrades over long contextsStart a fresh session per task instead of one long thread. Put the important constraint last.
The model is stateless; the harness re-sends everything“It forgot” is almost always a context-assembly problem, not a model problem.
Output is sampled from a probability distributionTwo identical prompts can give different answers. Never treat a single run as evidence.
Hallucination is the normal behaviour of a likelihood machineGround every factual claim in retrieved context, and verify APIs against the actual package.
The model has one input channel for instructions and dataA pull-request comment is executable input. Treat all repository content as untrusted.
An agent loop only improves if it gets a signalFast, reliable tests and a runnable build are the single biggest agent accelerant.
Tools are requests the harness executes, not model capabilitiesSecurity lives in the harness and the token scope, never in the prompt.
Reasoning spends tokens to buy accuracyMatch model and thinking budget to task difficulty, not to habit.

How to run it

The material is one thing; the format is yours. Four that work:

Skim

2 hours · solo

Read the concept map, every key idea callout in Part One, then all of Part Two. Enough to stop making the common mistakes.

Workshop

2 days · 6–20 people

Day one: Modules 1–7 with the labs in Module 14 interleaved. Day two: Part Two against your own repository. Finish by writing your real instruction files together.

Study group

6 weeks · 1 hour weekly

One module pair per week, one lab per week, one volunteer presenting. Slowest but it sticks best, and the discussion is where the real objections surface.

Reference

ongoing

Keep it in the repo. When someone asks why an instruction file must be short, send the Module 4 anchor rather than the answer.

What you need

  • For Part One: nothing. No maths beyond school algebra, no Python. Every figure is self-contained.
  • For Part Two: a GitHub repository you can push branches to, and Copilot enabled on it. A Business or Enterprise plan for the governance sections in Module 12 — read them anyway if you are on an individual plan, because they tell you what your organisation cannot currently see.
  • For the labs: a browser. Two labs are more interesting with a terminal.
Before you start

Part Two names specific files, features and model versions. Those move faster than any document can. Treat every name as a pointer to GitHub's own documentation rather than as a fact with a shelf life, and check anything you are about to standardise on. The mechanics in Part One have not changed since 2017 and are not about to.
