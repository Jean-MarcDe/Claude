01Wie ein LLM funktioniert

1Grundbegriffe

Was ist was

Artificial Intelligence (AI) — Sammelbegriff für Systeme, die Aufgaben lösen, für die man Intelligenz erwarten würde. Sagt nichts über die Technik.

Machine Learning (ML) — Die Regeln werden nicht programmiert, sondern von einem Suchverfahren aus Beispielen ermittelt. Ergebnis ist ein Model: eine Funktion mit gelernten Zahlen.

Deep Learning — Machine Learning mit vielschichtigen Neural Networks. Grundlage aller heutigen Sprach- und Bildmodelle.

Generative AI — Modelle, die neue Inhalte erzeugen (Text, Code, Bilder, Audio) statt nur zu klassifizieren.

Large Language Model (LLM) — Ein sehr großes Neural Network in Transformer-Architektur, trainiert darauf, das nächste Token eines Textes vorherzusagen. Beispiele: Claude, GPT, Gemini.

Supervised Learning — Training mit Eingaben und von Menschen vorgegebenen Soll-Ausgaben (Labels).

Self-Supervised Learning — Das Soll wird aus den Daten selbst gebildet: nächstes Token verdecken und vorhersagen. Kein Labeling nötig, deshalb praktisch unbegrenzt Trainingsmaterial. So werden LLMs trainiert.

Parameter — Die gelernten Zahlen eines Modells: Weights und Biases. Ein aktuelles großes LLM hat größenordnungsmäßig 10¹¹ davon.

Hyperparameter — Einstellungen, die ein Mensch vor dem Training festlegt und die nicht gelernt werden: Anzahl Layers, Learning Rate, Batch Size.

2Neural Network und Training

Wie die Parameter entstehen

Neuron — Die kleinste Einheit: bildet eine gewichtete Summe seiner Eingaben, addiert einen Bias und wendet eine Activation Function an.z = w₁x₁ + w₂x₂ + b    ŷ = σ(z)

Weight — Faktor, mit dem eine Eingabe multipliziert wird. Bestimmt, wie stark sie zählt.

Bias — Konstante, die zur Summe addiert wird. Verschiebt die Schwelle des Neurons.

Activation Function — Nichtlineare Funktion am Ausgang des Neurons (z. B. Sigmoid, ReLU). Ohne sie ließe sich jedes tiefe Netz zu einer einzigen linearen Schicht zusammenrechnen.

Layer — Eine Schicht von Neuronen. Frühe Layers erkennen einfache Muster, spätere kombinieren sie.

Forward Pass — Eine Eingabe läuft einmal durch alle Layers; am Ende steht die Vorhersage.

Loss — Eine einzige Zahl, die sagt, wie falsch die Vorhersage war. Sie ist die vollständige Spezifikation des Trainingsziels: Was der Loss nicht misst, wird nicht gezielt gelernt.

Cross-Entropy Loss — Der Loss für LLMs: −log der Wahrscheinlichkeit, die das Modell dem tatsächlich folgenden Token gegeben hat. Bestraft hart, wenn das Richtige für fast unmöglich gehalten wurde.

Gradient — Die Steigung des Loss bezüglich eines Parameters: Wie ändert sich der Fehler, wenn ich diesen Parameter leicht erhöhe?

Gradient Descent — Das Lernverfahren: jeden Parameter ein kleines Stück gegen seinen Gradient verschieben, sodass der Loss sinkt. Milliardenfach wiederholt.w ← w − η · ∂L/∂w

Learning Rate (η) — Die Schrittweite. Zu klein: Training kriecht. Zu groß: Jeder Schritt springt über das Minimum, das Training divergiert.

Batch / Stochastic Gradient Descent — Der Gradient wird nicht aus allen Daten berechnet, sondern aus einer kleinen zufälligen Stichprobe (Batch) geschätzt.

Backpropagation — Der Algorithmus, der in einem einzigen Rückwärtsdurchlauf (Backward Pass) per Chain Rule die Gradients aller Parameter berechnet. Backpropagation berechnet, Gradient Descent ändert – zwei verschiedene Vorgänge.

Overfitting / Generalization — Ein Modell kann Trainingsdaten auswendig lernen und bei Neuem versagen. Entscheidend ist das Verhalten auf ungesehenen Daten (Test Set).

Pretraining — Die lange, teure Phase: Next-Token Prediction auf riesigen Textmengen. Hier entsteht das Wissen.

Fine-Tuning — Nachtrainieren auf kleineren, gezielten Daten. Bei Chat-Modellen: das Frage-Antwort-Format.

RLHF (Reinforcement Learning from Human Feedback) — Nachtrainieren anhand menschlicher Bewertungen. Prägt Ton, Hilfsbereitschaft, Ablehnungsverhalten – und eine Neigung zuzustimmen.

Training Cutoff — Der Stichtag, an dem die Trainingsdaten enden. Alles danach kennt das Modell nur, wenn es im Context steht.

Inference — Die Nutzung des fertig trainierten Modells. Die Parameter sind eingefroren: Nichts, was ihr tippt, verändert das Modell.

Ob ein Modell eine Aufgabe beherrscht, steht in keiner Spezifikation. Das zeigt nur ein Test mit bekannten Antworten.

3Von Text zu Vorhersage

Was bei jedem einzelnen Token passiert

Token — Ein Textstück aus einem festen Vocabulary: ein Wort, ein Wortteil, ein Satzzeichen. Das Modell sieht ausschließlich Token-IDs, keine Buchstaben.

Tokenizer / Byte-Pair Encoding (BPE) — Zerlegt Text in Tokens. Das Vocabulary entsteht vor dem Training, indem häufige Zeichenfolgen schrittweise verschmolzen werden. Häufiges wird ein Token, Seltenes zerfällt in viele.

Vocabulary — Die Menge aller Tokens eines Modells, typischerweise 100.000–200.000 Einträge.

Embedding — Der Vektor (einige tausend Zahlen), der ein Token repräsentiert. Training ordnet die Vektoren so an, dass ähnlich verwendete Tokens nah beieinander liegen. Grundlage von Semantic Search und RAG.

Attention — Der Mechanismus, mit dem jedes Token Information von anderen Tokens holt. Jede Position stellt eine Query, bietet einen Key und liefert einen Value; das Ergebnis ist eine gewichtete Mischung.softmax(QKᵀ / √dₖ) · VAufwand wächst quadratisch mit der Länge.

Transformer — Die Architektur aller aktuellen LLMs: Dutzende gestapelte Blöcke aus Multi-Head Attention (bewegt Information zwischen Positionen) und Feed-Forward Network (verarbeitet Information an einer Position).

Logits — Die Rohwerte am Ende des Forward Pass: eine Zahl pro Token im Vocabulary.

Softmax — Wandelt Logits in Wahrscheinlichkeiten um, die sich zu 100 % summieren.

Sampling — Das nächste Token wird aus dieser Verteilung gezogen, nicht einfach das wahrscheinlichste genommen. Deshalb liefert dieselbe Anfrage verschiedene Antworten.

Temperature — Teilt die Logits vor dem Softmax. T < 1 schärft die Verteilung, T > 1 flacht sie ab und gibt Unwahrscheinlichem mehr Gewicht.

Top-p — Beschränkt das Ziehen auf die kleinste Menge von Tokens, deren Wahrscheinlichkeiten zusammen p ergeben. Schneidet den langen Rest ab.

Autoregression — Ein Token pro Forward Pass. Es wird an den Context angehängt, dann läuft alles erneut. Folgen: Output ist teuer, frühe Fehler pflanzen sich fort, und erzeugter Text ist von zugeliefertem nicht zu unterscheiden.

Reasoning / Thinking — Das Modell erzeugt zuerst Zwischenschritte (ein Notizblatt) und liest sie per Attention wieder ein, bevor es antwortet. Hilft bei mehrstufigen Problemen.

Reasoning Effort / Thinking Effort — Einstellung pro Aufgabe, wie viele Thinking Tokens das Modell aufwenden darf. Thinking Tokens werden als Output abgerechnet und sind oft nicht sichtbar.

4Wissen, Context, Hallucination

Was das Modell weiß – und was nicht

Zwei Wissensquellen

ParameterContext
Im Training gelernt, danach eingefrorenIn diesem Request mitgeschickt
Endet am Training CutoffAktuell und exakt
Kennt nichts InternesBegrenzt, kostet Tokens
Unscharf, verdichtetNach dem Request weg

Memory gibt es im Modell nicht. Was wie Erinnerung wirkt, ist Text, den der Harness erneut in den Context legt.

Context Window — Die maximale Eingabe in Tokens. Der Platz wird geteilt: System Prompt, Tool-Definitionen, Instructions, Files, History und euer Prompt konkurrieren. Der gesamte Inhalt wird bei jedem Request neu gesendet.

Lost in the Middle — Je voller das Fenster, desto unzuverlässiger wird Material gefunden, am schwächsten in der Mitte. Annehmen heißt nicht verwenden.

Compaction — Nähert sich der Context der Grenze, ersetzt der Harness die History durch eine Zusammenfassung. Details gehen dabei verloren. In der Copilot CLI startet das bei rund 80 %; die Schwellen variieren je Client.

Hallucination — Flüssige, aber falsche Ausgabe. Kein Schritt des Verfahrens prüft eine Aussage gegen die Wirklichkeit. Es ist derselbe Mechanismus, der richtige Antworten erzeugt, angewendet dort, wo die Trainingsdaten ihn nicht festgelegt haben. Gegenmittel sind strukturell: die Quelle in den Context legen, Tools rechnen und nachschlagen lassen, Belege verlangen und prüfen.

5Systeme um das Modell

Vom Modell zum Agent

Harness — Das Programm um das Modell: stellt den Context zusammen, liefert Tool-Definitionen, führt Tool Calls aus, entscheidet über Abbruch und Compaction. GitHub Copilot in VS Code ist ein Harness, Claude Code ein anderer. Dasselbe Modell verhält sich in verschiedenen Harnesses unterschiedlich.

System Prompt — Die Anweisungen des Harness-Herstellers, die vor allem anderen im Context stehen.

Tool — Eine Fähigkeit außerhalb von Text: Datei lesen, Terminalbefehl, Websuche, API-Aufruf. Beschrieben durch Name, Beschreibung und Parameter-Schema.

Tool Call — Das Modell gibt strukturierten Text aus (Tool-Name plus Argumente). Der Harness prüft die Permission, führt aus und hängt das Tool Result an den Context. Das Modell führt nie selbst etwas aus.

Agentic Loop — Beobachten, entscheiden, handeln, Ergebnis lesen, wiederholen – bis die Aufgabe erledigt ist. Zuverlässig wird das vor allem durch Rückmeldung in der Schleife (Tests, Build).

Agent — Ein Modell in einem Harness mit Tools und einer Agentic Loop. Kann handeln, nicht nur antworten.

Subagent — Ein Agent, den der Haupt-Agent für eine Teilaufgabe startet. Arbeitet in einem eigenen Context und liefert nur das Ergebnis zurück. Hält den Haupt-Context sauber.

RAG (Retrieval-Augmented Generation) — Zu einer Frage werden passende Textstellen gesucht (meist über Embeddings) und in den Context gelegt. Wirksamstes Einzelmittel gegen Hallucination. Fehler sind dann meist Suchfehler: prüfen, was abgerufen wurde.

MCP (Model Context Protocol) — Offener Standard, über den ein Harness externe Tools und Daten anbindet. Ein MCP Server ist ein Paket aus Tools.

Prompt Injection — Text in einem Dokument, einer Webseite oder einem Tool Result, der als Anweisung formuliert ist. Funktioniert, weil Anweisungen und Daten denselben Kanal benutzen.

Vorgehen

  1. Start mit Versatile oder Auto (wählt je Request; wo angeboten, mit „Optimize for“ Efficiency, Balance oder Intelligence).
  2. Runter auf Lightweight, wenn die Aufgabe mechanisch ist und das Ergebnis sofort sichtbar.
  3. Hoch auf Powerful, wenn mehrstufig, ein früher Fehler teuer – oder zwei Versuche gescheitert sind.
  4. Thinking Effort nur erhöhen, wenn wirklich geschlussfolgert werden muss. Bei Nachschlagen und Umformatieren kostet es nur.

Benchmarks und eigene Eval

Benchmarks taugen als erster Filter, nicht als Entscheidung: Kein Leaderboard misst eure Aufgabe, Testbedingungen variieren, und veröffentlichte Tests landen in späteren Trainingsdaten.

Mini-Eval (ein halber Tag): 5–10 echte Aufgaben mit bekanntem Sollergebnis. Kriterien vorher festlegen. Jede Aufgabe dreimal laufen lassen – ein einzelner Run misst den Zufall. Kosten und Dauer mit notieren.

Drei Token-Arten

Input — alles, was gesendet wird: der gesamte Context, bei jedem Request.

Cached Input — ein unveränderter Anfang des Context, den der Anbieter schon verarbeitet hat. Kostet etwa ein Zehntel bis ein Zwanzigstel. Stabile Instructions sparen also Geld; ein wechselnder Prefix zerstört den Cache.

Output — alles Erzeugte, inklusive Thinking Tokens. Kostet typischerweise das Fünffache des Inputs.

Rechenbeispiel (Sonnet 5.5, Start-Context 30K, 20 Agent-Steps, +4K je Step, 1K Output je Step): 1,55 Mio. Input-Tokens, rund 59 Credits mit Caching, rund 330 ohne. Bei 40 Steps: 134 Credits.

Was Credits frisst

  • Lange Sessions: Die History reist jedes Mal mit, die Input-Tokens wachsen quadratisch
  • Große Files und Tool Results im Context
  • Agent Loops mit vielen Steps
  • Hoher Thinking Effort für Routine
  • Powerful-Modell für Trivialaufgaben
  • Retries, weil die Aufgabe unklar war

Was hilft

  • Neuer Chat pro Aufgabe
  • Gezielte Files statt ganzer Ordner
  • Modell passend zur Aufgabe
  • Präziser Prompt: ein Run statt drei
  • Subagents für Recherche (eigener Context)
  • Kurze, stabile Instructions (Cache bleibt warm)
Die Modellkosten sind meist der kleinere Posten. Zwanzig Minuten Review kosten mehr als der Run. Am günstigsten ist der Weg mit den wenigsten Korrekturschleifen.

9Deutsch oder Englisch

Kosten messbar, Qualität differenziert

Kosten: Das Vocabulary ist auf Englisch und Code optimiert. Deutsch braucht für denselben Inhalt mehr Tokens – als Richtwert das 1,3- bis 1,5-Fache, bei Komposita mehr. Das wirkt auf Kosten und auf den Platz im Context Window. Der Faktor hängt vom Tokenizer ab: für eigene Texte messen, nicht schätzen. Qualität: Aktuelle große Modelle verstehen und schreiben Deutsch sehr gut. Der Abstand wächst bei kleinen Modellen, bei Fachterminologie und dort, wo Doku, Code und Fehlermeldungen ohnehin englisch sind.

WasEmpfehlung
Instructions, Skills, Agents, Prompt FilesEnglisch. Werden bei jedem Request gesendet; Begriffe sind eindeutig; teamübergreifend lesbar.
Code, Commits, FachbegriffeEnglisch. Fachbegriffe nie übersetzen (Gradient Descent, nicht „Gradientenabstieg“).
Ad-hoc im ChatDie Sprache, in der ihr am präzisesten formuliert. Präzision schlägt Sprache.

10Context Engineering

Bewusst entscheiden, was das Modell sieht

Was im Context steht (von oben nach unten)

  1. System Prompt des Harness
  2. Tool-Definitionen – Built-in und jeder MCP Server
  3. Custom Instructions und Skill-Beschreibungen
  4. Angehängte Files, geöffnete Datei, Selection
  5. History und Tool Results (größter Posten in Agent-Sessions)
  6. Euer Prompt – der kleinste Teil

In VS Code zeigt ein kleiner Kreis am Chat-Eingabefeld den Füllstand. In der Copilot CLI: /context und /compact.

Neuer Chat, wenn …

  • die Aufgabe wechselt
  • drei Korrekturen nichts gebracht haben (im Context stehen dann drei falsche Ansätze)
  • mehrere Compactions hinter euch liegen
  • ihr von Erkunden zu Umsetzen wechselt

Übergabenotiz: Lange Arbeit am Ende einer Session in fünf Zeilen zusammenfassen lassen (Ziel, Stand, Entscheidungen, offene Punkte, nächster Schritt) und die neue Session damit beginnen.

11Prompting

Sechs Bausteine, sechs Patterns
BausteinSchwachBelastbar
Ziel„Fix den Export“„Der CSV-Export bricht ab 10.000 Zeilen ab. Ziel: läuft für 1 Mio. Zeilen durch.“
Hintergrundfehlt„Läuft nightly in CI mit 2 GB Speicherlimit. Streaming ist erlaubt.“
Constraints„Mach es sauber“„Public API nicht ändern. Keine neue Dependency.“
Output-Format„Zeig mal“„Erst Plan in fünf Punkten, dann Diff, dann offene Fragen.“
Acceptance Criteriafehlt„Bestehende Tests grün, plus ein neuer Test mit 1 Mio. Zeilen.“
Umgang mit Lückenfehlt„Wenn etwas unklar ist: fragen, nicht raten. Annahmen auflisten.“

Die beiden roten Bausteine fehlen am häufigsten und verändern das Ergebnis am stärksten.

Beispiele zeigen (Few-Shot) — Ein gutes Beispiel für den gewünschten Output schlägt drei Absätze Beschreibung.

Das Warum nennen — „Keine neue Dependency, weil das Audit sechs Wochen dauert“ generalisiert besser als ein nacktes Verbot.

Positiv formulieren — Sagen, was passieren soll. Aktuelle Modelle nehmen Anweisungen wörtlich.

Erst Plan, dann Ausführung — Der Plan kostet einen Bruchteil und zeigt Missverständnisse, bevor Code entsteht.

Verify-Loop mitgeben — Tests, Build, Linter, Typecheck: Ein Agent, der sein Ergebnis selbst prüfen kann, wird deutlich zuverlässiger.

Neu starten statt flicken — Nach zwei Fehlversuchen: neuer Chat mit besserem Prompt, nicht die fünfte Korrektur.

Prompting Guides — Anthropic, OpenAI und Google veröffentlichen eigene, modellspezifische Guides. Den Guide für das meistgenutzte Modell einmal lesen (Abschnitt 16).

Agent Skills

.github/skills/ms-style/SKILL.md 
---
name: ms-style
description: Write or review user-facing docs
  following the Microsoft Writing Style Guide.
  Use for README files, how-to guides,
  release notes and UI text.
---
# Rules
- Sentence-style capitalization in headings.
- Second person, active voice, present tense.

Approved terms: references/word-list.md
After writing, run scripts/check_terms.py.

Progressive Disclosure: (1) name und description stehen immer im Context, rund 100 Tokens. (2) Die SKILL.md wird erst geladen, wenn das Modell den Skill für relevant hält. (3) references/ und scripts/ nur bei Bedarf.

Die description trägt die Hauptlast: Sie ist alles, was das Modell bei der Entscheidung sieht. Hineinschreiben, was der Skill tut und wann er greifen soll.

Eigenen Skill bauen – fünf Schritte

  1. Aufgabe dreimal von Hand im Chat lösen
  2. Was war jedes Mal gleich? Vom Agent in eine SKILL.md schreiben lassen
  3. Alles Exakte in Scripts auslagern: rechnen, validieren, formatieren
  4. description schärfen: wann greifen, wann nicht
  5. An drei echten Fällen testen, dann per Pull Request ins Repo

Gute Kandidaten: Styleguides (Google developer documentation style guide, Microsoft Writing Style Guide), Design-Vorlagen (Corporate Design, Slide-Templates), reproduzierbare Abläufe (Release Notes, Incident Report, Migrations- und Review-Checklisten).

Agent Skills sind ein offener Standard: Derselbe Ordner funktioniert in Copilot, Claude Code und anderen Agents. Copilot liest auch .claude/skills/ und .agents/skills/.

Hooks

.github/hooks/guard.json 
{
  "version": 1,
  "hooks": {
    "preToolUse": [{
      "type": "command",
      "command": "node .github/hooks/guard.cjs",
      "timeoutSec": 10
    }]
  }
}

Ein Hook ist ein Shell-Befehl, der deterministisch an einem Lifecycle-Event läuft. Er bekommt das Event als JSON auf stdin; ein preToolUse-Hook kann einen Tool Call mit "permissionDecision": "deny" ablehnen.

Events: sessionStart, userPromptSubmitted, preToolUse, postToolUse, preCompact, subagentStart, subagentStop, agentStop, sessionEnd. In VS Code noch Preview; Hooks ersetzen keine Sandbox und keine Org-Policy.

Prompt Files und Agent Plugins

Prompt File — eine gespeicherte Anfrage mit Platzhaltern unter .github/prompts/, aufgerufen per /name im Chat. Richtig, wenn dieselbe Anfrage regelmäßig wiederkommt, aber kein mehrstufiges Verfahren ist. Agent Plugin — ein installierbares Bündel aus Skills, Custom Agents, Hooks, MCP Servers und Slash Commands, verteilt über Marketplaces. Richtig, wenn ein Setup über Teams hinweg geteilt werden soll. Vor der Installation Herausgeber und Inhalt prüfen: Ein Plugin ist ausführbarer Code.

14Sicherheit und Verification

Prüfen ist euer Job – macht ihn euch leicht

Prompt Injection

Im Context ist alles Text. Das Modell kann nicht sicher unterscheiden, ob ein Satz von euch stammt oder aus einem README, Issue, PDF oder Tool Result. Das ist eine Eigenschaft der Architektur; eine allgemeine Lösung gibt es derzeit nicht.

Gefährliche Dreierkombination: vertrauliche Daten + nicht vertrauenswürdiger Inhalt + ausgehender Kanal. Treffen alle drei zusammen, kann ein Angreifer Daten abziehen. Eines der drei entfernen.

Gehört nicht in den Prompt: gültige Secrets, Tokens, Passwörter; personenbezogene Daten identifizierbarer Personen; Vertrauliches von Dritten. Gelangt ein Secret in einen Chat: rotieren.

Tool Approvals nicht reflexhaft auf „Always allow“ stellen, vor allem nicht für Terminal und Netzwerk.

Verification

Vorher: Acceptance Criteria festlegen, bevor die Arbeit beginnt. Währenddessen: dem Agent einen Verify-Loop geben. Danach: Prüfbarkeit einfordern – Diff statt Prosa, Quelle zu jeder Aussage, Liste der Annahmen.

Besondere Sorgfalt: alles Unumkehrbare (Senden, Deployen, Löschen), Schreibzugriff auf Geteiltes, erste Durchläufe nach Modell- oder Konfigurationswechsel.

15Zehn Regeln

Für morgen früh
  1. Das Modell sagt Tokens vorher. Geprüft wird nichts – außer von euch.
  2. Was nicht im Context steht, existiert nicht.
  3. Neuer Chat pro Aufgabe.
  4. Das kleinste Modell, das die Aufgabe schafft.
  5. Ziel, Constraints, Acceptance Criteria – vor dem Start.
  6. Erst Plan, dann Agent.
  7. Gebt dem Agent einen Verify-Loop.
  8. Was sich wiederholt, wird ein Skill.
  9. Instructions bitten, Hooks und Permissions garantieren.
  10. Dauerhaftes auf Englisch: kurz und widerspruchsfrei.
