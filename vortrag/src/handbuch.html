01Wie ein LLM funktioniert

1Grundbegriffe

Einordnung der Begriffe

Artificial Intelligence (AI) — Sammelbegriff für Systeme, die Aufgaben lösen, für die man Intelligenz voraussetzen würde. Der Begriff legt keine bestimmte Technik fest.

Machine Learning (ML) — Die Regeln werden nicht programmiert, sondern von einem Suchverfahren aus Beispielen ermittelt. Ergebnis ist ein Model: eine Funktion mit gelernten Zahlen.

Deep Learning — Machine Learning mit Neural Networks aus vielen Layern. Grundlage aller heutigen Sprach- und Bildmodelle.

Generative AI — Modelle, die neue Inhalte erzeugen (Text, Code, Bilder, Audio) statt nur zu klassifizieren.

Large Language Model (LLM) — Ein sehr großes Neural Network in Transformer-Architektur, trainiert darauf, das nächste Token eines Textes vorherzusagen. Beispiele: Claude, GPT, Gemini.

Supervised Learning — Training mit Eingaben und von Menschen vorgegebenen Soll-Ausgaben (Labels).

Self-Supervised Learning — Das Soll wird aus den Daten selbst gebildet: nächstes Token verdecken und vorhersagen. Labels von Menschen sind nicht nötig, daher steht sehr viel Trainingsmaterial zur Verfügung. So werden LLMs trainiert.

Parameter — Die gelernten Zahlen eines Modells: Weights und Biases. Ein aktuelles großes LLM hat größenordnungsmäßig 10¹¹ davon.

Hyperparameter — Einstellungen, die ein Mensch vor dem Training festlegt und die nicht gelernt werden: Anzahl der Layer, Learning Rate, Batch Size.

2Neural Network und Training

Wie die Parameter entstehen

Neuron — Die kleinste Einheit: bildet eine gewichtete Summe seiner Eingaben, addiert einen Bias und wendet eine Activation Function an.z = w₁x₁ + w₂x₂ + b    ŷ = σ(z)

Weight — Faktor, mit dem eine Eingabe multipliziert wird. Bestimmt, wie stark sie zählt.

Bias — Konstante, die zur Summe addiert wird. Verschiebt die Schwelle des Neurons.

Activation Function — Nichtlineare Funktion am Ausgang des Neurons (z. B. Sigmoid, ReLU). Ohne sie ließe sich jedes Netz, unabhängig von der Zahl der Layer, zu einem einzigen linearen Layer zusammenfassen.

Layer — Eine Schicht von Neuronen. Frühe Layer erkennen einfache Muster, spätere kombinieren sie.

Forward Pass — Eine Eingabe läuft einmal durch alle Layer; am Ende steht die Vorhersage.

Loss — Eine einzige Zahl, die sagt, wie falsch die Vorhersage war. Sie ist die vollständige Spezifikation des Trainingsziels: Was der Loss nicht misst, wird nicht gezielt gelernt.

Cross-Entropy Loss — Der Loss für LLMs: −log der Wahrscheinlichkeit, die das Modell dem tatsächlich folgenden Token gegeben hat. Der Loss ist hoch, wenn das Modell dem richtigen Token eine sehr geringe Wahrscheinlichkeit gegeben hat.

Gradient — Die Steigung des Loss bezüglich eines Parameters: Er gibt an, wie sich der Fehler ändert, wenn dieser Parameter leicht erhöht wird.

Gradient Descent — Das Lernverfahren: Jeder Parameter wird ein kleines Stück gegen seinen Gradienten verändert, sodass der Loss sinkt. Der Schritt wird milliardenfach wiederholt.w ← w − η · ∂L/∂w

Learning Rate (η) — Die Schrittweite. Ist sie zu klein, kommt das Training nur langsam voran. Ist sie zu groß, springt jeder Schritt über das Minimum, und das Training divergiert.

Batch / Stochastic Gradient Descent — Der Gradient wird nicht aus allen Daten berechnet, sondern aus einer kleinen zufälligen Stichprobe (Batch) geschätzt.

Backpropagation — Der Algorithmus, der in einem einzigen Rückwärtsdurchlauf (Backward Pass) per Chain Rule die Gradienten aller Parameter berechnet. Gradient Descent verwendet diese Gradienten anschließend, um die Parameter anzupassen.

Overfitting / Generalization — Ein Modell kann Trainingsdaten auswendig lernen und bei Neuem versagen. Entscheidend ist das Verhalten auf ungesehenen Daten (Test Set).

Pretraining — Die lange, teure Phase: Next-Token Prediction auf riesigen Textmengen. In dieser Phase entsteht das Wissen des Modells.

Fine-Tuning — Nachtrainieren auf kleineren, gezielten Daten. Bei Chat-Modellen: das Frage-Antwort-Format.

RLHF (Reinforcement Learning from Human Feedback) — Nachtrainieren anhand menschlicher Bewertungen. Prägt Ton, Hilfsbereitschaft und Ablehnungsverhalten, aber auch eine Neigung zuzustimmen.

Training Cutoff — Der Stichtag, an dem die Trainingsdaten enden. Alles danach kennt das Modell nur, wenn es im Context steht.

Inference — Die Nutzung des fertig trainierten Modells. Die Parameter sind eingefroren: Eingaben verändern das Modell nicht.

Ob ein Modell eine Aufgabe beherrscht, lässt sich nur durch Tests mit bekannten Antworten feststellen.

3Von Text zu Vorhersage

Was bei jedem einzelnen Token passiert

Token — Ein Textstück aus einem festen Vocabulary: ein Wort, ein Wortteil, ein Satzzeichen. Das Modell sieht ausschließlich Token-IDs, keine Buchstaben.

Tokenizer / Byte-Pair Encoding (BPE) — Zerlegt Text in Tokens. Das Vocabulary entsteht vor dem Training, indem häufige Zeichenfolgen schrittweise verschmolzen werden. Häufige Wörter sind ein Token, seltene bestehen aus mehreren.

Vocabulary — Die Menge aller Tokens eines Modells, typischerweise 100.000–200.000 Einträge.

Embedding — Der Vektor (einige tausend Zahlen), der ein Token repräsentiert. Training ordnet die Vektoren so an, dass ähnlich verwendete Tokens nah beieinander liegen. Grundlage von Semantic Search und RAG.

Attention — Der Mechanismus, mit dem jedes Token Information von anderen Tokens holt. Jede Position stellt eine Query, bietet einen Key und liefert einen Value; das Ergebnis ist eine gewichtete Mischung.softmax(QKᵀ / √dₖ) · VAufwand wächst quadratisch mit der Länge.

Transformer — Die Architektur aller aktuellen LLMs: mehrere Dutzend gestapelte Blöcke aus Multi-Head Attention (bewegt Information zwischen Positionen) und Feed-Forward Network (verarbeitet Information an einer Position).

Logits — Die Rohwerte am Ende des Forward Pass: eine Zahl pro Token im Vocabulary.

Softmax — Wandelt Logits in Wahrscheinlichkeiten um, die sich zu 100 % summieren.

Sampling — Das nächste Token wird aus dieser Verteilung gezogen, nicht einfach das wahrscheinlichste genommen. Deshalb liefert dieselbe Anfrage verschiedene Antworten.

Temperature — Teilt die Logits vor dem Softmax. T < 1 schärft die Verteilung, T > 1 flacht sie ab und gibt Unwahrscheinlichem mehr Gewicht.

Top-p — Beschränkt das Ziehen auf die kleinste Menge von Tokens, deren Wahrscheinlichkeiten zusammen p ergeben. Schneidet den langen Rest ab.

Autoregression — Ein Token pro Forward Pass. Es wird an den Context angehängt, dann läuft alles erneut. Daraus folgt: Output-Tokens sind teuer, frühe Fehler pflanzen sich fort, und erzeugter Text ist von zugeliefertem nicht zu unterscheiden.

Reasoning / Thinking — Das Modell erzeugt zuerst Zwischenschritte, vergleichbar mit einem Notizblatt, und verarbeitet sie per Attention, bevor es antwortet. Hilft bei mehrstufigen Problemen.

Reasoning Effort / Thinking Effort — Einstellung pro Aufgabe, wie viele Thinking Tokens das Modell aufwenden darf. Thinking Tokens werden als Output abgerechnet und sind oft nicht sichtbar.

4Wissen, Context, Hallucination

Herkunft und Grenzen des Wissens

Zwei Wissensquellen

ParameterContext
Im Training gelernt, danach eingefrorenIn diesem Request mitgeschickt
Endet am Training CutoffAktuell und exakt
Kennt nichts InternesBegrenzt, kostet Tokens
Unscharf, verdichtetNach dem Request weg

Memory gibt es im Modell nicht. Was wie Erinnerung wirkt, ist Text, den der Harness erneut in den Context legt.

Context Window — Die maximale Eingabe in Tokens. Der Platz wird geteilt: System Prompt, Tool-Definitionen, Instructions, Dateien, Verlauf und Prompt teilen sich das Fenster. Der gesamte Inhalt wird bei jedem Request neu gesendet.

Lost in the Middle — Je voller das Fenster, desto unzuverlässiger nutzt das Modell den Inhalt, am schlechtesten den in der Mitte. Was im Context steht, wird also nicht zwingend verwendet.

Compaction — Nähert sich der Context der Grenze, ersetzt der Harness den bisherigen Verlauf durch eine Zusammenfassung. Details gehen dabei verloren. In der Copilot CLI startet das bei rund 80 %; die Schwellen variieren je Client.

Hallucination — Flüssige, aber falsche Ausgabe. Kein Schritt des Verfahrens prüft eine Aussage gegen die Wirklichkeit. Es ist derselbe Mechanismus, der richtige Antworten erzeugt, angewendet dort, wo die Trainingsdaten ihn nicht festgelegt haben. Gegenmaßnahmen: die Quelle in den Context geben, Tools rechnen und nachschlagen lassen, Belege verlangen und prüfen.

5Systeme um das Modell

Harness, Tools und Agents

Harness — Das Programm um das Modell: stellt den Context zusammen, liefert Tool-Definitionen, führt Tool Calls aus, entscheidet über Abbruch und Compaction. GitHub Copilot in VS Code ist ein Harness, Claude Code ein anderer. Dasselbe Modell verhält sich in verschiedenen Harnesses unterschiedlich.

System Prompt — Die Anweisungen des Harness-Herstellers, die vor allem anderen im Context stehen.

Tool — Eine Fähigkeit außerhalb von Text: Datei lesen, Terminalbefehl, Websuche, API-Aufruf. Beschrieben durch Name, Beschreibung und Parameter-Schema.

Tool Call — Das Modell gibt strukturierten Text aus (Tool-Name plus Argumente). Der Harness prüft die Permission, führt aus und hängt das Tool Result an den Context. Das Modell führt nie selbst etwas aus.

Agentic Loop — Beobachten, entscheiden, handeln, Ergebnis lesen, wiederholen, bis die Aufgabe erledigt ist. Zuverlässig wird das vor allem durch Rückmeldungen innerhalb der Schleife (Tests, Build).

Agent — Ein Modell in einem Harness mit Tools und einer Agentic Loop. Kann handeln, nicht nur antworten.

Subagent — Ein Agent, den der Haupt-Agent für eine Teilaufgabe startet. Arbeitet in einem eigenen Context und liefert nur das Ergebnis zurück. Der Context des Haupt-Agent bleibt dadurch klein.

RAG (Retrieval-Augmented Generation) — Zu einer Frage werden passende Textstellen gesucht (meist über Embeddings) und in den Context gelegt. Wirksamste einzelne Maßnahme gegen Hallucination. Verbleibende Fehler entstehen meist bei der Suche; daher prüfen, welche Textstellen abgerufen wurden.

MCP (Model Context Protocol) — Offener Standard, über den ein Harness externe Tools und Daten anbindet. Ein MCP Server ist ein Paket aus Tools.

Prompt Injection — Text in einem Dokument, einer Webseite oder einem Tool Result, der als Anweisung formuliert ist. Funktioniert, weil Anweisungen und Daten denselben Kanal benutzen.

Vorgehen

  1. Ausgangspunkt: Versatile oder Auto (wählt das Modell je Request; wo angeboten, mit „Optimize for“ Efficiency, Balance oder Intelligence).
  2. Wechsel zu Lightweight, wenn die Aufgabe mechanisch ist und sich das Ergebnis sofort beurteilen lässt.
  3. Wechsel zu Powerful, wenn die Aufgabe mehrstufig ist, ein früher Fehler teuer wird oder zwei Versuche gescheitert sind.
  4. Thinking Effort nur erhöhen, wenn die Aufgabe mehrere Schlussfolgerungen erfordert. Beim Nachschlagen und Umformatieren entstehen nur Mehrkosten.

Benchmarks und eigene Evaluation

Benchmarks eignen sich zur Vorauswahl, nicht als alleinige Entscheidungsgrundlage: Keine Rangliste misst die eigene Aufgabe, Testbedingungen variieren, und veröffentlichte Tests landen in späteren Trainingsdaten.

Eigene Evaluation (ein halber Tag): 5–10 echte Aufgaben mit bekanntem Sollergebnis. Kriterien vorher festlegen. Jede Aufgabe dreimal ausführen, weil ein einzelner Durchlauf wegen des Samplings nicht aussagekräftig ist. Kosten und Dauer ebenfalls notieren.

Drei Token-Arten

Input — alles, was gesendet wird: der gesamte Context, bei jedem Request.

Cached Input — ein unveränderter Anfang des Context, den der Anbieter schon verarbeitet hat. Kostet etwa ein Zehntel bis ein Zwanzigstel. Gleichbleibende Instructions senken also die Kosten; ändert sich der Anfang, wird der Cache ungültig.

Output — alles Erzeugte, inklusive Thinking Tokens. Kostet typischerweise das Fünffache des Inputs.

Rechenbeispiel (Sonnet 5.5, Start-Context 30K, 20 Agent-Schritte, +4K je Schritt, 1K Output je Schritt): 1,55 Mio. Input-Tokens, rund 59 Credits mit Caching, rund 330 ohne. Bei 40 Schritten: 134 Credits.

Kostentreiber

  • Lange Sitzungen: Der Verlauf wird jedes Mal mitgesendet, die Input-Tokens wachsen quadratisch
  • Große Dateien und Tool Results im Context
  • Agentic Loops mit vielen Schritten
  • Hoher Thinking Effort für Routineaufgaben
  • Powerful-Modell für einfache Aufgaben
  • Wiederholungen wegen unklarer Aufgabenstellung

Gegenmaßnahmen

  • Neuer Chat pro Aufgabe
  • Einzelne Dateien statt ganzer Ordner anhängen
  • Modell passend zur Aufgabe wählen
  • Präziser Prompt: ein Durchlauf statt drei
  • Subagents für Recherche (eigener Context)
  • Kurze, gleichbleibende Instructions (der Cache bleibt gültig)
Die Modellkosten sind meist der kleinere Posten: Zwanzig Minuten Arbeitszeit für die Prüfung kosten mehr als der Durchlauf. Am günstigsten ist das Vorgehen mit den wenigsten Korrekturschleifen.

9Deutsch oder Englisch

Tokenbedarf, Qualität und Empfehlung je Verwendung

Kosten: Das Vocabulary ist auf Englisch und Code optimiert. Deutsch braucht für denselben Inhalt mehr Tokens, als Richtwert das 1,3- bis 1,5-Fache, bei Komposita mehr. Das wirkt auf Kosten und auf den Platz im Context Window. Der Faktor hängt vom Tokenizer ab und sollte für eigene Texte gemessen werden. Qualität: Aktuelle große Modelle verstehen und schreiben Deutsch sehr gut. Der Abstand zum Englischen wächst bei kleinen Modellen, bei Fachterminologie und dort, wo Dokumentation, Code und Fehlermeldungen ohnehin englisch sind.

VerwendungEmpfehlung
Instructions, Skills, Agents, Prompt FilesEnglisch. Werden bei jedem Request gesendet; Begriffe sind eindeutig; teamübergreifend lesbar.
Code, Commits, FachbegriffeEnglisch. Fachbegriffe nicht übersetzen (Gradient Descent, nicht „Gradientenabstieg“).
Einzelne Anfragen im ChatDie Sprache, in der man am präzisesten formuliert. Die Genauigkeit ist wichtiger als die Sprache.

10Context Engineering

Bewusst entscheiden, was das Modell sieht

Was im Context steht (von oben nach unten)

  1. System Prompt des Harness
  2. Tool-Definitionen: integrierte Tools und jeder MCP Server
  3. Custom Instructions und Skill-Beschreibungen
  4. Angehängte Dateien, geöffnete Datei, Markierung
  5. Verlauf und Tool Results (größter Anteil in Agent-Sitzungen)
  6. Prompt: der kleinste Teil

In VS Code zeigt ein kleiner Kreis am Chat-Eingabefeld den Füllstand. In der Copilot CLI: /context und /compact.

Neuer Chat, wenn …

  • die Aufgabe wechselt
  • drei Korrekturen erfolglos waren (im Context stehen dann drei falsche Ansätze)
  • bereits mehrere Compactions stattgefunden haben
  • die Arbeit vom Erkunden zum Umsetzen übergeht

Übergabenotiz: Längere Arbeit am Ende einer Sitzung in fünf Zeilen zusammenfassen lassen (Ziel, Stand, Entscheidungen, offene Punkte, nächster Schritt) und die neue Sitzung damit beginnen.

11Prompting

Bausteine eines Prompts und bewährte Vorgehensweisen
BausteinZu ungenauGenau
Ziel„Reparier den Export“„Der CSV-Export bricht ab 10.000 Zeilen ab. Ziel: läuft für 1 Mio. Zeilen durch.“
Hintergrundfehlt„Läuft jede Nacht in der CI-Pipeline mit 2 GB Speicherlimit. Streaming ist erlaubt.“
Randbedingungen„Mach es sauber“„Öffentliche API nicht ändern. Keine neue Dependency.“
Ausgabeformat„Zeig mal“„Erst Plan in fünf Punkten, dann Diff, dann offene Fragen.“
Acceptance Criteriafehlt„Bestehende Tests grün, plus ein neuer Test mit 1 Mio. Zeilen.“
Umgang mit Lückenfehlt„Wenn etwas unklar ist: fragen, nicht raten. Annahmen auflisten.“

Die beiden roten Bausteine fehlen am häufigsten und verändern das Ergebnis am stärksten.

Beispiele zeigen (Few-Shot) — Ein gutes Beispiel für die gewünschte Ausgabe wirkt besser als eine lange Beschreibung.

Begründung angeben — „Keine neue Dependency, weil das Audit sechs Wochen dauert“ wird zuverlässiger auf ähnliche Fälle übertragen als ein Verbot ohne Begründung.

Positiv formulieren — Angeben, was geschehen soll, statt nur, was zu unterlassen ist. Aktuelle Modelle befolgen Anweisungen wörtlich.

Erst Plan, dann Ausführung — Ein Plan kostet wenige Tokens und macht Missverständnisse sichtbar, bevor Code entsteht.

Prüfschleife vorgeben — Tests, Build, Linter, Typecheck: Ein Agent, der sein Ergebnis selbst prüfen kann, arbeitet deutlich zuverlässiger.

Neu beginnen statt nachbessern — Nach zwei Fehlversuchen ist ein neuer Chat mit einem besseren Prompt wirksamer als weitere Korrekturen.

Prompting Guides — Anthropic, OpenAI und Google veröffentlichen eigene, modellspezifische Guides. Es lohnt sich, den Guide für das meistgenutzte Modell zu lesen (Abschnitt 16).

Agent Skills

.github/skills/ms-style/SKILL.md 
---
name: ms-style
description: Write or review user-facing docs
  following the Microsoft Writing Style Guide.
  Use for README files, how-to guides,
  release notes and UI text.
---
# Rules
- Sentence-style capitalization in headings.
- Second person, active voice, present tense.

Approved terms: references/word-list.md
After writing, run scripts/check_terms.py.

Progressive Disclosure: (1) name und description stehen immer im Context, rund 100 Tokens. (2) Die SKILL.md wird erst geladen, wenn das Modell den Skill als passend einstuft. (3) references/ und scripts/ nur bei Bedarf.

Die description ist entscheidend: Nur sie liegt dem Modell bei der Auswahl vor. Sie sollte angeben, was der Skill tut und wann er verwendet werden soll.

Eigenen Skill erstellen in fünf Schritten

  1. Die Aufgabe dreimal von Hand im Chat lösen
  2. Die gleichbleibenden Teile vom Agent in eine SKILL.md schreiben lassen
  3. Exakte Teilschritte in Skripte auslagern: rechnen, validieren, formatieren
  4. description präzisieren: wann der Skill verwendet werden soll und wann nicht
  5. An drei echten Fällen testen, dann per Pull Request ins Repository aufnehmen

Gute Kandidaten: Styleguides (Google developer documentation style guide, Microsoft Writing Style Guide), Design-Vorlagen (Corporate Design, Folienvorlagen), reproduzierbare Abläufe (Release Notes, Incident Report, Migrations- und Review-Checklisten).

Agent Skills sind ein offener Standard: Derselbe Ordner funktioniert in Copilot, Claude Code und anderen Agents. Copilot liest auch .claude/skills/ und .agents/skills/.

name: Reviewer

Review the code supplied in the request.
Report findings with file and line references.

Abgrenzung: Ein Skill enthält Wissen und Verfahren, die jeder Agent nutzen kann. Ein Agent ist eine Rolle mit eigenem Auftrag und eingeschränkten Tools.

  "hooks": {
    "preToolUse": [{
      "type": "command",
      "command": "node .github/hooks/guard.cjs",
      "timeoutSec": 10
    }]
  }
}

Ein Hook ist ein Shell-Befehl, der deterministisch bei einem Lifecycle-Ereignis ausgeführt wird. Er erhält das Ereignis als JSON über stdin; ein preToolUse-Hook kann einen Tool Call mit "permissionDecision": "deny" ablehnen.

Ereignisse: sessionStart, userPromptSubmitted, preToolUse, postToolUse, preCompact, subagentStart, subagentStop, agentStop, sessionEnd. In VS Code noch im Preview-Status; Hooks ersetzen weder eine Sandbox noch die Richtlinien der Organisation.

Prompt Files und Agent Plugins

Prompt File — eine gespeicherte Anfrage mit Platzhaltern unter .github/prompts/, aufgerufen per /name im Chat. Richtig, wenn dieselbe Anfrage regelmäßig wiederkommt, aber kein mehrstufiges Verfahren ist. Agent Plugin — ein installierbares Bündel aus Skills, Custom Agents, Hooks, MCP Servers und Slash Commands, verteilt über Marketplaces. Richtig, wenn ein Setup über Teams hinweg geteilt werden soll. Vor der Installation Herausgeber und Inhalt prüfen: Ein Plugin ist ausführbarer Code.

14Sicherheit und Überprüfung

Prompt Injection, vertrauliche Daten, Prüfung der Ergebnisse

Prompt Injection

Der Context besteht nur aus Text. Das Modell kann nicht sicher unterscheiden, ob ein Satz vom Nutzer stammt oder aus einem README, Issue, PDF oder Tool Result. Das ist eine Eigenschaft der Architektur; eine allgemeine Lösung gibt es derzeit nicht.

Riskante Kombination: vertrauliche Daten + nicht vertrauenswürdiger Inhalt + ausgehender Kanal. Treffen alle drei zusammen, kann ein Angreifer Daten abgreifen. Mindestens eines der drei ist auszuschließen.

Gehört nicht in den Prompt: gültige Secrets, Tokens, Passwörter; personenbezogene Daten identifizierbarer Personen; Vertrauliches von Dritten. Gelangt ein Secret in einen Chat, muss es ersetzt werden.

Tool Approvals nicht pauschal auf „Always allow“ stellen, vor allem nicht für Terminal und Netzwerk.

Überprüfung

Vorher: Acceptance Criteria festlegen, bevor die Arbeit beginnt. Währenddessen: dem Agent eine Prüfschleife vorgeben. Danach: prüfbare Ergebnisse verlangen: Diff statt Beschreibung, Quelle zu jeder Aussage, Liste der Annahmen.

Verwendung des ErgebnissesPrüftiefe
Erkunden, PrototypDurchsicht
Eigene MeinungsbildungStichproben
Pull Request, KollegenJede Änderung gelesen und verstanden
Produktion, Vertrag, externVollständig; Zahlen unabhängig nachgerechnet

Besondere Sorgfalt: alle nicht umkehrbaren Aktionen (Senden, Deployen, Löschen), Schreibzugriff auf Geteiltes, erste Durchläufe nach Modell- oder Konfigurationswechsel.

15Zehn Regeln

Für die tägliche Arbeit
  1. Das Modell sagt Tokens vorher. Die Prüfung der Ergebnisse bleibt Aufgabe des Menschen.
  2. Das Modell kennt nur, was im Context steht.
  3. Für jede Aufgabe einen neuen Chat beginnen.
  4. Das kleinste Modell wählen, das die Aufgabe löst.
  5. Ziel, Randbedingungen und Acceptance Criteria vorab festlegen.
  6. Zuerst einen Plan erstellen lassen, dann den Agent starten.
  7. Dem Agent eine Prüfschleife vorgeben.
  8. Wiederkehrende Abläufe als Skill ablegen.
  9. Verbindliche Regeln über Hooks und Permissions durchsetzen.
  10. Dauerhafte Dateien auf Englisch, kurz und widerspruchsfrei.
